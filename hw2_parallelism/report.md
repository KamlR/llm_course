# ДЗ 2. Оптимизация обучения на одной GPU

В работе исследуется ускорение обучения Qwen3 на одной NVIDIA A100 80GB. Основная метрика — полезные токены в секунду; дополнительно сравниваются GPU-память и validation loss. Проведено 14 экспериментов с размером батча и накоплением градиентов, checkpointing, torch.compile, FlashAttention 2, padding-free, packing и Liger, включая их сочетания. Короткие прогоны использовались для отбора конфигураций, а выбранные варианты обучались с нуля по 300 секунд на той же GPU, что и baseline.

Из всей серии наиболее удачными оказались два результата:

- **[Лучший по скорости — эксперимент 13](#experiment-13):** FlashAttention 2 + packing + padding-free + Liger, batch 64 / accumulation 1. Скорость **27 443,16 токена/с**, ускорение **3,90× к baseline**, validation loss **6,0677**. Это выбранная конфигурация по главной метрике задания.
- **[Лучший по validation loss — эксперимент 11](#experiment-11):** FlashAttention 2 + padding-free без packing. Validation loss **5,1027**, скорость **19 189,18 токена/с** (**2,73× к baseline**), пиковая выделенная память **15,18 ГиБ**.

Оба результата получены за 300 секунд обучения с нуля. Они показывают, что максимальная скорость обработки токенов и минимальный loss за одинаковое время могут достигаться разными конфигурациями. Ниже приведены все эксперименты, включая неудачный запуск с OOM и варианты, которые не улучшили скорость.

## Эксперимент 1. Baseline

### Описание эксперимента

Цель — измерить скорость, потребление GPU-памяти и лосс исходной конфигурации. Этот запуск служит точкой отсчёта для последующих оптимизаций.

Запущен исходный [train.py](baseline/train.py) без изменений, с `TRAIN_SECONDS=300`. Модель обучалась с нуля на одной NVIDIA A100 80GB PCIe. Использовано окружение из [Dockerfile.runtime](baseline/Dockerfile.runtime): PyTorch 2.6.0 с CUDA 11.8, Transformers 4.56.2, TRL 0.23.1, Datasets 3.6.0 и Accelerate 1.6.0.

**Модель и данные.** Используется Qwen3 из шаблона: 12 слоёв, `hidden_size=2048`, `intermediate_size=8192`, 16 голов внимания, 8 KV-голов, `head_dim=128`, `use_cache=False`. Токенизатор — `ai-forever/rugpt3small_based_on_gpt2`, датасет — `wikimedia/wikipedia`, конфигурация `20231101.ru`; ревизии закреплены в коде.

Подготовка и разделение данных соответствуют шаблону ДЗ 2: из первых 50 500 статей первые 500 выделены под validation, остальные 50 000 — под train. Из статьи берутся первые 8 непустых абзацев длиной не менее 80 символов. После токенизации сохраняются абзацы с минимум 32 токенами, текст ограничивается 511 токенами и дополняется EOS. Максимальная длина последовательности — 512. Финальная оценка проводится на первых 512 подготовленных validation-примерах.

| Параметр | Значение |
|---|---|
| Batch size на GPU | 32 |
| Gradient accumulation | 2 |
| Эффективный batch size | 64 примера на шаг оптимизатора |
| Attention | SDPA |
| Activation checkpointing | Выключен |
| Sequence packing / padding-free | Выключены; используется padding внутри батча |
| `torch.compile` | Выключен |
| Liger kernels | Выключены |

После запуска артефакты перенесены локально в [baseline/](baseline/); в копии кода сохранён исходный путь запуска. Полная конфигурация находится в [train.py](baseline/train.py).

`S = tokens_per_second эксперимента / 7035.419588231213`.

Итоговое ускорение будет рассчитано для лучшей конфигурации, обученной с нуля в течение 300 секунд на той же GPU.

### Вывод

Baseline успешно завершил обучение: за 300,59 секунды выполнено 369 шагов оптимизатора и обработано около 2,10 млн полезных токенов. Полученная скорость **7035,42 токена/с** принята за базовый уровень для сравнения оптимизаций.

По логу средний train loss за первые 10 шагов составил 11,2276, а за интервал, завершившийся на шаге 360, — 6,8399. Это показывает снижение обучающего loss в течение запуска. Финальный validation loss равен **6,6001**; его динамика не измерялась, поскольку шаблон выполняет validation только после обучения.

Пиковая выделенная память составила 41,24 ГиБ, зарезервированная — 43,44 ГиБ. Это оставляет запас относительно 80 ГБ GPU и позволяет исследовать увеличение batch size. Ускорение от этого изменения пока не измерено.

Результат характеризует только исходную конфигурацию. Сравнение механизмов оптимизации, их сочетаний и объяснение минимум трёх наблюдаемых эффектов будут добавлены после соответствующих экспериментов.

## Эксперимент 2. Batch 64, gradient accumulation 1 — запуск с OOM

### Описание эксперимента

Гипотеза: обработка 64 примеров за один проход вместо двух микробатчей по 32 может уменьшить накладные расходы и увеличить полезные токены в секунду. Эффективный batch size сохраняется: `32 × 2 = 64 × 1 = 64`.

Модель инициализирована с нуля на той же NVIDIA A100 80GB PCIe, что и baseline. По сравнению с baseline изменены только следующие настройки:

| Параметр | Baseline | Этот эксперимент |
|---|---|---|
| `per_device_train_batch_size` | 32 | 64 |
| `gradient_accumulation_steps` | 2 | 1 |
| `TRAIN_SECONDS` | 300 | 90 |
| `output_dir` | `results/baseline` | `batch64_90s` |

Модель, токенизатор, данные и split, длина 512, BF16/TF32, SDPA, оптимизатор, learning rate, scheduler, seed и подсчёт метрик сохранены. Checkpointing, packing, padding-free, compile, Liger и offloading выключены.

### Результаты

Запуск завершился ошибкой `torch.OutOfMemoryError` при обратном проходе. Сохранены [код и настройки](batch64_90s/train.py), [полный лог](batch64_90s/train.log) и [код выхода 1](batch64_90s/exit_code.txt).

| Метрика | Результат |
|---|---|
| Статус | Неуспешный запуск: CUDA out of memory |
| Запланированная длительность | 90 с |
| Фактическая полная длительность обучения | Не сохранена из-за аварийного завершения |
| Последний шаг, зафиксированный в логе | 10, на отметке 11,174 с |
| Итоговое число шагов оптимизатора | Не сохранено; подтверждено не менее 10 |
| Полезные токены/с | Итоговая метрика не получена |
| Пиковая GPU-память | Итоговая метрика не получена |
| Validation loss | Не получен: evaluation не выполнялась |
| Train loss в последнем интервале логирования | 11,2277 |
| Ускорение S | Не рассчитывается |

В момент ошибки PyTorch сообщил о 67,34 ГиБ выделенной памяти и ещё 6,40 ГиБ зарезервированной, но не выделенной под тензоры памяти. Процесс занимал 75,38 ГиБ; на GPU оставалось 3,71 ГиБ свободной памяти при запросе ещё 6,14 ГиБ. Это диагностика в момент OOM, **не замена пиковой метрике** из `summary.json`.

Файл `summary.json` не создан: шаблон записывает его только после успешного завершения обучения и validation. Отсутствующие метрики не восстанавливаются по неполному логу.

### Вывод

Увеличение микробатча с 32 до 64 при сохранении эффективного batch size привело к нехватке GPU-памяти. Накопление градиентов позволяет обрабатывать эффективный batch 64 меньшими частями; перенос всех 64 примеров в один проход увеличивает объём одновременно хранимых промежуточных вычислений.

Первые 10 шагов прошли, но это не гарантировало устойчивость всего запуска. При динамическом padding потребление памяти может меняться между батчами; влияние длины конкретного батча на этот OOM отдельно не измерялось.

Конфигурация `batch=64, accumulation=1` в текущем окружении не подходит для итогового запуска без дополнительных мер экономии памяти. Её скорость и качество сравнить с baseline по итоговым метрикам нельзя. Этот неудачный запуск сохраняется для анализа ограничения памяти и не заменяет успешную конфигурацию в требуемом наборе экспериментов.

## Эксперимент 3. Activation checkpointing

### Описание эксперимента

Гипотеза: activation checkpointing уменьшит объём хранимых активаций и пиковую GPU-память ценой повторных вычислений при обратном проходе. Эксперимент проверяет этот механизм отдельно от изменения batch size.

Обучение выполнено с нуля на той же NVIDIA A100 80GB PCIe, что и baseline. Использованы исходные batch size 32 и gradient accumulation 2, эффективный batch size — 64.

| Параметр | Baseline | Этот эксперимент |
|---|---|---|
| `gradient_checkpointing` | `False` | `True` |
| `gradient_checkpointing_kwargs` | `{"use_reentrant": False}` | Без изменений |
| `TRAIN_SECONDS` | 300 | 90 |
| `output_dir` | `results/baseline` | `checkpointing_90s` |

Остальные настройки сохранены: модель, токенизатор, данные и split, максимальная длина 512, BF16/TF32, SDPA, `adamw_torch_fused`, learning rate `3e-4`, `constant_with_warmup` с 200 шагами warmup, weight decay 0,01, seed и data seed 42. Packing, padding-free, compile, Liger и offloading выключены. Подсчёт метрик и процедура validation не изменены.

### Результаты

Запуск успешно завершён. Сохранены [summary.json](checkpointing_90s/summary.json), [код и настройки](checkpointing_90s/train.py) и [лог обучения](checkpointing_90s/train.log).

| Метрика | Baseline, 300 с | Checkpointing, 90 с |
|---|---:|---:|
| Фактическая длительность обучения, с | 300,590 | 90,069 |
| **Полезные токены/с** | **7035,42** | **6044,63** |
| Полезные токены/с с учётом разогрева | 6988,20 | 5869,27 |
| Пиковая выделенная GPU-память, ГиБ | 41,237 | 17,391 |
| Пиковая зарезервированная GPU-память, ГиБ | 43,439 | 23,971 |
| Validation loss | 6,6001 | 8,2358 |
| Число шагов оптимизатора | 369 | 93 |
| Всего полезных обучающих токенов | 2 100 584 | 528 642 |
| Шаги в основном замере скорости | 359 | 83 |
| Длительность основного замера, с | 290,402 | 77,947 |
| Среднее время шага после разогрева, с | 0,809 | 0,939 |
| Число целевых токенов при validation | 50 694 | 50 694 |
| Отношение скорости к baseline, S | 1,000× | 0,859× |

`S = 6044.630267258846 / 7035.419588231213 = 0.85917`.

По этим замерам скорость ниже baseline на **14,08%**, а пиковая выделенная память меньше на **23,85 ГиБ (57,83%)**. Это предварительное сравнение короткого запуска с 300-секундным baseline; оно не является итоговым ускорением лучшей конфигурации.

### Вывод

Activation checkpointing показал ожидаемый компромисс: существенное уменьшение памяти сопровождалось снижением скорости. Такой результат согласуется с механизмом checkpointing: часть промежуточных активаций не сохраняется, а вычисляется повторно во время backward. Отдельный профиль вычислений не снимался.

При текущем batch size 32 checkpointing сам по себе не улучшил главную метрику — полезные токены в секунду. Однако освободившаяся память позволяет проверить сочетание checkpointing с большим batch size, который без этой оптимизации завершился OOM. Успех и скорость такого сочетания пока не измерены.

Validation loss 8,2358 выше, чем у baseline, но это не доказывает ухудшение качества из-за checkpointing: запуск длился 90 вместо 300 секунд, сделал 93 вместо 369 шагов и обработал меньше токенов. Кроме того, он завершился до окончания 200 шагов warmup learning rate.

Пиковая память также измерялась на более коротком участке обучения. Для окончательного вывода об итоговой конфигурации потребуется предусмотренный заданием запуск на 300 секунд.

## Эксперимент 4. torch.compile — короткий запуск

### Описание эксперимента

Гипотеза: компиляция модели может ускорить повторяющиеся вычисления, но первоначальная компиляция требует времени. Проверяем, удастся ли получить полезный замер скорости в коротком 90-секундном запуске.

Модель инициализирована с нуля на той же NVIDIA A100 80GB PCIe. По сравнению с baseline изменены только три настройки:

| Параметр | Baseline | Этот эксперимент |
|---|---|---|
| `torch_compile` | `False` | `True` |
| `TRAIN_SECONDS` | 300 | 90 |
| `output_dir` | `results/baseline` | `compile_90s` |

Batch size — 32, gradient accumulation — 2, checkpointing выключен, attention — SDPA. Модель, токенизатор, данные и split, длина 512, BF16/TF32, оптимизатор, learning rate, scheduler, seed и подсчёт метрик сохранены. Packing, padding-free, Liger и offloading выключены.

Запуск выполнен в новом контейнере; каталоги кеша TorchInductor и Triton расположены внутри контейнера в `/tmp` и не перенесены из предыдущих запусков. Отдельного предварительного разогрева компиляции не было.

### Результаты

Обучение и финальная validation завершились без ошибок. Сохранены [summary.json](compile_90s/summary.json), [код и настройки](compile_90s/train.py) и [лог](compile_90s/train.log).

|---|---:|
| Запланированная длительность обучения, с | 90 |
| Фактическая длительность обучения, с | 109,934 |
| Число шагов оптимизатора | 1 |
| Всего полезных обучающих токенов | 6439 |
| Шаги после первых 10 разогревочных | 0 |
| **Полезные токены/с — `tokens_per_second`** | **Не определены (`null`)** |
| Полезные токены/с с учётом разогрева | 58,57 |
| Пиковая выделенная GPU-память, ГиБ | 26,019 |
| Пиковая зарезервированная GPU-память, ГиБ | 26,318 |

Первый шаг оптимизатора вместе с первоначальной компиляцией занял весь бюджет времени. Callback проверяет лимит после шага, поэтому остановка произошла через 109,93 секунды вместо 90. Чистое время компиляции отдельно не измерялось.

В исходном подсчёте скорости первые 10 шагов исключаются. Здесь выполнен всего один шаг, поэтому `measured_steps=0` и `tokens_per_second=null`. Значение 58,57 токена/с включает начальные затраты и не заменяет основную метрику задания.

### Вывод

Короткого запуска оказалось недостаточно, чтобы оценить скорость обучения после компиляции. Результат показывает значительную стоимость первого шага, но не позволяет утверждать, что `torch.compile` ускоряет или замедляет установившееся обучение относительно baseline.

Validation loss 11,2346 получен после единственного шага обучения. Сравнивать его с качеством baseline после 369 шагов как эффект компиляции некорректно. Память также измерена лишь на одном шаге и не характеризует пик на всём наборе батчей.

Для проверки потенциала этой конфигурации нужен отдельный запуск с нуля на 300 секунд на той же GPU, с сохранением исходного таймера и правил подсчёта метрик. До получения более 10 шагов и численной `tokens_per_second` этот запуск не считается полноценным замером скорости для выбора лучшей конфигурации.

## Эксперимент 5. Liger kernels

### Описание эксперимента

Гипотеза: специализированные вычислительные ядра Liger уменьшат затраты на выполнение операций модели и потребление GPU-памяти. Проверяем их отдельно от компиляции, checkpointing и packing.

## Эксперимент 13. FA2 + packing + Liger, batch 64 / accumulation 1, 300 секунд

### Описание эксперимента

Гипотеза: обработка 64 упакованных блоков за один forward/backward вместо двух микробатчей по 32 уменьшит накладные расходы и увеличит полезные токены в секунду. Эффективный batch сохраняется: `32 × 2 = 64 × 1 = 64` блока на обновление весов.

Запуск выполнен с нуля на той же NVIDIA A100 80GB PCIe с лимитом 300 секунд. По сравнению с экспериментом 10 изменены только batch size, gradient accumulation и папка результатов:

| Параметр | Прежний кандидат | Этот эксперимент |
|---|---|---|
| `per_device_train_batch_size` | 32 | 64 |
| `gradient_accumulation_steps` | 2 | 1 |
| `output_dir` | `flash_attention2_packing_liger_300s` | `flash_attention2_packing_liger_batch64_300s` |

Остальные настройки сохранены: FlashAttention 2, `packing=True`, стратегия `bfd`, `padding_free=True`, `use_liger_kernel=True`, максимальная длина блока 512. Checkpointing, compile и offloading выключены.

Модель, токенизатор, исходные данные и split, BF16/TF32, `adamw_torch_fused`, learning rate `3e-4`, scheduler `constant_with_warmup` с 200 шагами warmup, weight decay 0,01, seed/data seed 42, подсчёт метрик и финальная validation не изменены. Использован новый контейнер без переноса кеша Triton.

### Результаты

Запуск успешно завершён без OOM. Сохранены [summary.json](flash_attention2_packing_liger_batch64_300s/summary.json), [код и настройки](flash_attention2_packing_liger_batch64_300s/train.py) и [лог](flash_attention2_packing_liger_batch64_300s/train.log).

В этом измерении увеличение микробатча при сохранении эффективного batch дало небольшой выигрыш: среднее время обновления сократилось с 1,211 до 1,165 секунды, а основная метрика выросла до **27 443,16 токена/с**. Результат согласуется с уменьшением накладных расходов при обработке одного большого микробатча вместо двух меньших; профиль операций отдельно не снимался.

Ускорение позволило выполнить 254 обновления вместо 244 и обработать 8,12 млн полезных токенов вместо 7,80 млн за тот же временной бюджет. Validation loss немного снизился до 6,0677. Лучший validation loss среди проведённых запусков по-прежнему у FA2 + padding-free без packing: **5,1027** при 19 189,18 токена/с. Максимум скорости и минимум loss достигнуты разными конфигурациями.

## Эксперимент 14. FA2 + packing + Liger, batch 128 + checkpointing, 300 секунд

### Описание эксперимента

Гипотеза: activation checkpointing снизит память, необходимую для активаций, а увеличение микробатча до 128 блоков даст дополнительное ускорение. Проверяем, компенсирует ли больший batch затраты на повторные вычисления.

Модель обучалась с нуля на той же NVIDIA A100 80GB PCIe с лимитом 300 секунд. По сравнению с экспериментом 13 изменены три настройки:

| Параметр | Лидер: batch 64 | Этот эксперимент |
|---|---|---|
| `per_device_train_batch_size` | 64 | 128 |
| `gradient_checkpointing` | `False` | `True` |
| `output_dir` | `flash_attention2_packing_liger_batch64_300s` | `flash_attention2_packing_liger_batch128_checkpointing_300s` |

Gradient accumulation остаётся 1, поэтому эффективный batch вырос с 64 до **128 упакованных блоков на обновление**. Checkpointing использует исходное `gradient_checkpointing_kwargs={"use_reentrant": False}`.

Сохранены FlashAttention 2, packing со стратегией `bfd`, padding-free и Liger. Compile и activation offloading выключены. Модель, токенизатор, данные и split, длина 512, BF16/TF32, оптимизатор `adamw_torch_fused`, learning rate `3e-4`, scheduler `constant_with_warmup` с 200 шагами warmup, weight decay 0,01, seed/data seed 42, подсчёт метрик и финальная validation не изменены.

Гипотеза о дополнительном ускорении не подтвердилась: сочетание batch 128 с checkpointing дало 23 514,12 токена/с против 27 443,16 у batch 64 без checkpointing. Более крупный микробатч не компенсировал дополнительные затраты в этой конфигурации.

Поскольку одновременно изменены batch size и checkpointing, этот запуск измеряет результат их сочетания; отдельный вклад каждого изменения здесь не выделен. Batch 128 без checkpointing не проверялся.

Validation loss 7,8566 хуже результата batch 64 и baseline. За бюджет выполнено лишь 109 обновлений, а warmup в 200 шагов не завершился. Эффективный batch также удвоен.
